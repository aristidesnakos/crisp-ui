This is the tool the [Training tracker](/tools/training-tracker) page describes, as code you install and own. It is the same five patterns wired together: **See → Decide → Act → Confirm → Record**. Eighteen made-up people must complete safeguarding training. Three are overdue and four are due within 30 days. A manager reminds them, signs off whoever has done it, and every step lands in the record.

Try it in the preview. The seven people who need attention are already selected: press **Send reminder** and confirm. Switch **View as** to Sam Osei, who is staff, and the send and sign-off are refused. Press **Call the server directly** to see the server refuse him too, and record it. Turn on "Set the clock to 10pm" to see quiet hours stop a send. Nothing is saved or sent, and the page forgets everything on reload.

## Usage

```tsx
import { TrainingTracker } from "@/components/training-tracker"
```

With no props it runs on the in-memory server, as in the preview. For your own data, pass your own server and the signed-in user:

```tsx
<TrainingTracker
  server={myServer} // three methods that call your API
  currentUser={session.user} // { id, name, role } from your session
  timeZone="Europe/London"
/>
```

| Prop           | Type                    | Description                                                                                             |
| -------------- | ----------------------- | ------------------------------------------------------------------------------------------------------- |
| `server`       | `TrainingTrackerServer` | Your three calls. Omit it to use the in-memory demo server and its demo controls.                       |
| `currentUser`  | `TrackerUser`           | `{ id, name, role }` from your session, where `role` is `"staff"`, `"manager"` or `"admin"`.            |
| `initialState` | `TrackerState`          | The first state, if you already fetched it. Otherwise the screen calls `load()`.                        |
| `timeZone`     | `string`                | IANA zone for times in the record. Defaults to the tracker's own zone. The demo server also runs in it. |
| `locale`       | `string`                | BCP 47 locale for dates. Default `"en-GB"`.                                                             |

It also takes the props of a `div`, including `className`.

### How each stage hands to the next

| Stage   | Pattern                                                                                      | It takes                             | It hands on                                                              |
| ------- | -------------------------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| See     | [`status-strip`](/docs/components/status-strip), [`data-table`](/docs/components/data-table) | The people and records from `load()` | The selected people. The strip counts come from the same records.        |
| Decide  | [`alert-rules`](/docs/components/alert-rules) (`summarizeRule`) and `planReminder`           | The selected people                  | Who gets a reminder, who is left out and why, and a preview of the email |
| Act     | [`confirm-send`](/docs/components/confirm-send)                                              | The count and `checkReminderSend`    | One send that succeeds, is refused or fails, and one entry in the record |
| Confirm | A sign-off with a required reason (`checkSignOff`)                                           | A person and a written reason        | A person marked up to date, and one entry in the record                  |
| Record  | [`audit-timeline`](/docs/components/audit-timeline)                                          | The events your server wrote         | Nothing, except that the counts above now include what was just recorded |

## Rules and checks

These are the rules the "Make it yours" instructions ask your assistant to keep. The in-memory server follows each one, and `tests/training-tracker.test.ts` in the Real Good Site repo proves it. Your server must do the same.

- **Show the number of people before any reminder goes out.** The button says "Send reminder to 7 people", and nothing goes until you confirm "Send to 7 people?". People who are up to date, have no valid email address or appear twice are left out, and the screen says so.
- **A sign-off needs a written reason.** A blank reason, or one of only spaces, is refused by the screen and again by the server.
- **Every reminder, sign-off and failure adds one entry to the record, written by the server.** A send to seven people is one entry, not seven. A refusal or a failed send is one entry too.
- **No reminders between 9pm and 8am.** The server checks its own clock in the tracker's time zone (`inQuietHours`, built on `isQuietTime` from `alert-rules`). The demo runs on a clock fixed to daytime so it works at any hour; a real server uses the real clock.
- **Emails contain the person's first name and the training name, nothing else personal.** `buildReminderEmail` takes only the first name and the training name. One email goes to each person, so nobody sees who else was reminded.
- **Only managers and admins act.** Staff can look. The server checks the role from the session, not from the browser.

The four checks, and where each is proved:

1. **Reminding 7 people adds exactly one entry to the record.** Test "check 1". In the preview, send to the seven selected people and the record grows by one.
2. **A sign-off without a reason is refused.** Test "check 2", which calls the server with an empty and a blank reason.
3. **Someone who is not a manager cannot send reminders, even by calling the server directly.** Test "check 3". In the preview, view as Sam Osei and press **Call the server directly**.
4. **Everything can be done with the keyboard alone.** The repo has no browser test setup, so check this by hand: Tab to the views and the row checkboxes and press Space to select, Tab to **Send reminder**, press Enter, then Enter on **Send** (or Tab to **Cancel**, which returns focus to the button). Then Tab to **Person**, choose with the arrow keys, type a reason, Tab to **Sign off** and press Enter. Every control shows a focus ring, and each result is announced.

### Replace the in-memory server

The screen talks to a `TrainingTrackerServer` and to nothing else. Change one place: pass your own object with the same three methods, backed by your sign-in and your database, then delete `training-tracker-server.ts`.

```ts
const myServer: TrainingTrackerServer = {
  load: () => fetch("/api/training").then(read), // people, records, rule, events
  sendReminders: ({ personIds }) =>
    post("/api/training/reminders", { personIds }), // -> { sent, personIds, skipped }
  signOff: ({ personId, reason }) =>
    post(`/api/training/people/${personId}/sign-off`, { reason }),
}
```

`read` and `post` are yours: they throw an `Error` with a readable message on a non-2xx answer, which is what the screen shows. The `userId` argument the demo passes exists only because it has no session; a real server takes the user from the session and ignores any id in the body. On the server, reuse `checkReminderSend`, `checkSignOff`, `planReminder` and `buildReminderEmail` from `lib/training-tracker-lib.ts`, and write each event with `buildAuditEvent` in the same step as the action. The screen refetches with `load()` after every call, so what you see is what the server holds.

## What it does not do

- **It is a UI only.** It shows state and asks for decisions. It sends nothing, stores nothing and checks no one.
- **Hiding a button is not access control.** Your server must verify the user and the role on every call, and refuse otherwise.
- **The server writes the audit events.** A browser that records its own actions can be closed or edited. The timeline only displays.
- **The reminder days are shown, not run.** Reminders go when a manager presses Send. Scheduled reminders and the escalation in the rule are your server's job (see `remindersDue` in `alert-rules`).
- **The in-memory server is a stand-in.** It forgets everything on reload, delivers no email, and the "View as" switch is not a login.
- **One requirement per tracker.** Track another kind of training with a second tracker, or extend the types.
- **No certificate uploads or spreadsheet import.** Add them in your own app if you need them.
- **It is not compliance.** Real Good Site does not make a tool compliant with any law or standard.
- **Not tested with a screen reader.** This composition has not been checked with one. Run your own keyboard and screen reader check before relying on it.

## Examples by sector

Example data only. Each is the same tracker with the nouns changed: rename the requirement, replace the people, keep the rules.

- **Education: safeguarding training.** Staff at a school renew it every year. The safeguarding lead signs off with the certificate seen. Reminders use first names only and never go between 9 pm and 8 am.
- **Manufacturing: forklift licences.** Operators renew every three years. The warehouse manager signs off after the practical test. The record shows who was reminded and when.
- **Engineering: site inductions.** Contractors complete one before their first day on site. The site manager signs off. Anyone overdue is listed first.
- **Health: fire safety training.** Staff at a dental practice renew it every year. The practice manager signs off. The email names the training and nothing about the person's record.
